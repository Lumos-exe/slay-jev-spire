# 原生事务确认重构与六局实测

日期：2026-10-05。最终原生桥接版本 0.3.3，事务协议版本 1，规则版本 ironclad-5。

## 根因与架构变化

旧确认器把“前后快照中能找到某种效果变化”当成“输入已经执行”的依据。这两个概念不同：选中的牌可以先放回再抽回；瓶装遗物可以只更新描述；动作也可能打开另一个选择界面，而不是立刻完成整张牌的效果。

新的线上确认路径不依赖这些卡牌特例：

```text
生成合法动作 → 写入 pending-action.json → 发送带 ID 的命令
             → 原生接受 → 下一个原生可决策边界 → 匹配回执后提交
```

每条动作携带唯一 ID、游戏进程 epoch、预期状态 revision 和原命令。原生端先检查版本、单条在途事务和重复 ID，再调用 CommunicationMod 原有执行器；下一次原生可决策边界才把它标为 settled。

- **回执丢失**：查询同一 ID；未观察到接受时，最多进行有界的同 ID 重投。
- **已经接受**：只查询和等待，绝不换一个 ID 重发同一动作。
- **状态过期**：原生端在执行前拒绝；控制器重新观察和规划。
- **控制器恢复**：读取持久化的在途 ID，先核对回执，再做新决定。
- **游戏进程换 epoch**：不盲目重放旧进程中的动作。
- **模型调用时状态变了**：丢弃未发送决定，重新规划，不再直接停机。
- **上下文超限**：进行更小的比较，所有候选都参与；认证或非法输出不当作临时错误重试。
- **临时模型服务故障**：只对只读推理进行有限重试，不等同于重试游戏操作。

“settled”表示游戏处理这条输入后重新交出了控制权。若一张牌打开选牌界面，原输入可以 settled，接下来的选牌仍是另一条事务；它不表示整张牌的所有后续效果都已完成。

效果判断已分离到 `effects.py`。`effect_evidence` 只是旁路审计，缺少证据或审计报错都不能否决匹配的原生回执。旧特例仍可服务旧格式离线回放，但完整线上 Jev 入口强制要求新协议，不会悄悄退回旧确认方式。

对于本地尚未专门建模、但原生端已经提供合法选项的界面，新协议允许直接代理原生选项并等待事务回执；不会凭空生成鼠标坐标。已知界面的坏数据仍然拒绝处理。

主要实现：`transactions.py`、`session.py`、`effects.py`、`ActionProtocol.java`、`TransactionLedger.java`。

## 实战反馈带来的其他改进

1. **显示名称与原生 ID 分离。** 系统对照了原版目录及 Java `POWER_ID` 常量，修复 `Paper Frog`、`Boot`、`Flex`（失去临时力量）和 `NoBlockPower` 的识别，加入全体已声明支持 ID 的一致性测试。
2. **守护者 Sharp Hide。** 对照原版确认它按攻击牌触发一次，排在该牌效果之后、该牌自身消耗处理之前，不应按多段攻击每击重复扣血。击杀时仍保留未验证队列行为的观测边界。
3. **候选与 END 分开比较。** 先选最佳行动方案，再与立即结束回合比较；END 仍可选，避免大量相近行动方案分散单项概率后让 END 获胜。
4. **地精大块头的永久代价直接展示。** 候选直接列出技能引起的敌方力量增长，而不只藏在复杂局面引用里。
5. **构筑信息对称。** 摘要加入每击基础伤害、费用、多段/条件、虚无与自损，避免只突出抽牌和格挡。没有把基础伤害冒充最终伤害，也没有硬编码必买某张牌。
6. **提供原生营火描述与当前地图节点。** 路线分析从实际节点沿可见边计算可达资源。五局后核对发现营火 description 是 protected 字段，原导出未生效；统一改用支持继承和私有/受保护字段的 `NativeFields`。第六局第 10 层实际返回“回复最大生命的30%(28)”，46/94 HP 时选择休息，后续观测为 74 HP。这项以真实字段验证为准，没有拿编译通过代替验收。
7. **数据表达压缩。** 牌序共享、结果差量、局面共享与独立战术摘要并存，保留全部候选；有真实超限局面的完整展开等价测试。

本轮没有调整原有 `_quality` 的伤害/承伤权重。

## 验收边界

稳定性通过了上述六局及原生故障注入验证，但这不是“所有界面和模组永远不会失败”的证明。格式损坏、未知 epoch、持续服务故障等仍会明确停止，保留在途事务，避免危险重发。

**整局通关为 0/6，策略仍未达标。** 第五局进入第二幕是实际进展，但不能宣称胜率提高已得到统计证明。持续成长敌人的击杀节奏、跨回合价值和构筑选择仍是后续策略工作的重点；它们已经不再与“输入有没有被执行”混在同一确认器里。

单元测试覆盖：丢回执、重复 ID、陈旧 revision、换 epoch、控制器恢复、同状态结算、旁路审计失败、未知原生选项、原生 ID、上下文压缩及多阶段比较。本机 316 passed、3 skipped；Windows 319 passed。Windows 另有原生账本和继承字段读取的 Java 断言测试，均通过。

继续实测可在 Windows 交互桌面运行：

```powershell
.venv\Scripts\python.exe tools\play_series.py --seeds 953716482 953716483 953716484 --directory logs\series\new-batch
```

使用新的目录开始新批次，使用原目录恢复未完成批次。驱动只关闭已正常 GAME_OVER 且无在途事务的游戏；技术停止会保留现场。运行结果必须把技术停止和战败分别报告。
