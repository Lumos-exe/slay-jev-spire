# ABC 预测信息实验：预先固定的方案

日期：2026-10-05。用户确认使用同一组完整合法牌序，单独比较预测信息的影响。主实验为 `design_version: 2`，目录 `logs/abc/20261005-controlled`。

## 条件

- A：完整的已保存游戏状态和候选牌序；不提供预测结果。
- B：相同状态和牌序，加敌人剩余 HP、预计承伤、回合后玩家 HP、剩余能量、格挡、是否战斗获胜、预测范围。直接显示为 `simple_result`，不藏进差分引用。
- C：包含与 B 逐字段相同的 `simple_result`，再加现有详细预测，包括状态效果、牌堆、后续局面、偷钱及观察边界等。

每个配对使用同样的候选身份、顺序、共同原生状态和指令。不同条件不向模型透露 A/B/C 标签。移除旧的策略偏好上下文，保留实际近期操作记录。三组都允许根据牌序重新判断；没有奖励权重评分。

主实验采用一次 HTTP 请求处理全部候选，不做自动分组、不重试。上下文超限作为可用性失败单独统计，不伪装成模型作出了错误选择。这能避免把“预测信息是否有用”与“分组筛选方式”混为一谈。既有流水线分组请求的运行数据可以另外描述，不并入主实验的选择质量。

## 样本与重复

8 个保存的真实战斗局面，3 个条件，每条件重复 3 次，共 72 次判断。

| 局面 | 用途 |
|---|---|
| 异常局 step 80 | 小地精攻击/防御取舍，无预设最优标签 |
| step 87 | 有确定无药斩杀 |
| step 89 | 有确定无药斩杀 |
| step 134 | 大块头成长与当前承伤取舍，无加权评分 |
| step 138 | 武装选择与攻防取舍，无预设最优标签 |
| step 152 | 不利残局，无预设最优标签 |
| 保存的抽牌/上下文局面 | 信息边界与输入规模 |
| 慢请求 step 229 | 149 个候选的输入规模与接口耗时 |

固定随机种子 `20261005`。每次重复随机排列局面和候选，同一配对中的 ABC 候选顺序保持相同；随机轮换三组请求先后。实验期间没有游戏控制器调用 Jev。记录请求模型名和每个成功响应的实际模型版本；版本变化立即停止，不能混合比较。

## 指标

1. 可用性：有效候选返回、上下文超限、其他接口失败，均保留分母。
2. 性能：每组输入字符数、服务报告的输入/输出 token、单次请求 wall time、中位数与高分位数。不把本地枚举耗时混进接口耗时。
3. 确定斩杀：仅在两个已核实局面上，由独立的原生基础伤害与易伤算术检查所选牌序，不读取规划器的 `combat_won` 或收益评分。报告这两例的成功数和失败数，不称为全游戏胜率。
4. 其他局面：报告选择分布、重复一致性、三组的相同/不同选择及完整牌序，供盲评和后续真实游戏实验。没有依据时不硬标“最优”。

这是小型配对先导实验。两个斩杀局面来自同一场战斗，重复调用不等于新增独立局面；不据此宣称统计显著或通关能力优劣。A/B/C 若同样命中斩杀，只能说明在这两个简单任务上结果信息没有显示额外收益。

## 格式预试与主实验分开

先执行的一轮 `20261005-pilot` 保留全部 72 条记录，但它的 B 使用差分引用，C 另外有直观战术摘要，混入了结果展示方式的差异。因此它只作为格式预试，不用于主结论。修正后的主实验仍使用相同 8 个局面、同一随机化方案和 3 次重复，重新请求全部三组；没有复用旧 A 的计时结果。修正发生在主实验开始前，不因主实验的输赢改变样本或条件。

## 可复查性

先保存 `cases.json`、状态/候选哈希及 `manifest.json`，随后才发请求。每次保存完整模型输入、候选短标签映射、响应选择、概率元数据、耗时与版本。所有请求只读，不执行游戏动作。结果文件支持按预定顺序恢复，已完成观察不重跑。

运行：

```powershell
.venv\Scripts\python.exe tools\abc_experiment.py --directory logs\abc\20261005-controlled --repeats 3
```
