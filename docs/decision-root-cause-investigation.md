# 决策根因调查：模型、代码与接口边界

日期：2026-10-05。本次只做代码审查、隔离复现及只读 API 对照，没有更换线上策略或重新开始游戏。

## 结论先行

不能把所有失败归为“模型不行”，也不能认为只是确认器或枚举出了错。

1. **有可复现的代码缺陷**：历史恢复跨局污染；计划复用遗漏会改变费用的字段。
2. **有明确的架构契约缺口**：预测字段混合时间点；知识与建议混放后整块删除；模型能力/接口限制未独立建模；实际 HTTP 记录不足。
3. **对首局 Boss 第 6 回合的致死 END，已排除这份输入上的关键算术、候选映射和执行误发**。新的实际 HTTP 记录证明，服务端确实会在完整正确输入下直接返回 END。
4. **决策协议不稳定**：同一字节级请求也出现不同结果；改变排列或增加解释没有稳定改善。聚焦当前生存或缩小到两项能正确回答，但不证明它能可靠解决宽泛的整局最优化任务。

因此要重建的是可验证的游戏状态、信息边界、决策任务和评估闭环，而不只是换提示词或重新排列文件。

对象：运行 `dc7cb83e-d857-41e2-9897-f55b3c9e2463`，step 227。

- 玩家：25 HP、3 能量、0 格挡、无能力修正。
- 敌人：两只大史莱姆，各 62 HP，当前攻击分别 16 和 11；中间另有一个已死亡 Boss 实例。

### 独立算术复核

另写了只支持这份原生手牌的计算器，不调用 `rules.play()` 或 `rules.outcome()`，逐项复核全部 85 个候选的敌人 HP、格挡、能量、玩家掉血及回合后 HP。85/85 一致。

### 编码、映射、执行复核

- 使用真实 SDK 和受控 HTTP 响应，把 85 个可能返回的短 ID 逐一送入实际解析路径；85/85 映射回正确原候选。

- 原生回执 ID 为 `8191cdb4e0af43e58897c044df91115e`，revision 从 227 到 228，结果观察为玩家 HP 0。

这不是“模型选了武装，但程序错按了结束回合”。不过旧日志未保存那一次历史原始 HTTP 响应，不能补造不存在的抓包；本次另保存了真实新请求和响应。

## 2. 新的 30 次实际请求对照

每种条件 5 次，随机轮换请求先后。所有成功响应均为 `jev-1.13.0`，全部 30 次正常返回。

前五种条件保留全部 85 个候选。仅两项对照改变候选集合，明确作为诊断控制，不能与完整问题当作同一性能测试。

| 条件 | 活过当前攻击 | 选到死亡 | 说明 |
|---|---:|---:|---|
| 原始 B | 4/5 | 1/5 | 5 次实际 HTTP 请求的字节哈希相同 |
| 只打乱选项排列 | 1/5 | 4/5 | 保持原短 ID、状态、结果、问题不变；HTTP 中确实发生重排 |
| 增加时间点/单位说明 | 2/5 | 3/5 | 说明 HP 是绝对剩余值、能量是 END 前未用值等 |
| 增加可读牌序与选牌名称 | 2/5 | 3/5 | 保留原引用，增加等价文字描述 |
| 明确只问当前生存 | 5/5 | 0/5 | 不再让同一问题同时承担整局取舍 |
| END 与一个已核实存活方案二选一 | 5/5 | 0/5 | 保留完整状态，仅缩小选项集合 |

30 次的原始响应 `choice` 与 SDK 解析一致，映射都正确，概率键集合与请求候选集合一致；这批响应的 choice 也全部是报告概率的最大项。

### 能据此判断什么

- 代码没有在这些请求里截掉活路或错译 ID，网络端本身会返回错误选择。
- 原始 B 在完全相同的请求下也不稳定，不能把一次成功回放当作修复完成。
- 模型能识别这个局面的存活方案；问题不是简单的“永远算不出 25－15”。
- 大候选集合、问题范围和表示方式会影响实际表现。把更多文字塞进去，没有得到稳定改善。

### 不能据此判断什么

- 不能宣布“重排一定更差”“加解释一定有害”，每组只有 5 次且来自同一个局面。
- 不能断言已经证明概率稀释、注意力位置偏差或某种内部推理机制。外部响应无法直接揭示内部原因。
- 不能把聚焦生存的 5/5 当作整局胜率，也不能立刻把所有决策都改成只求本回合不掉血。
- 两项对照只证明小问题能答对，不能据此任意砍掉原有 83 个选项。

## 3. 确认的代码问题

### 3.1 历史恢复把种子当成本局身份

位置：`session.py:276` 的 `_restore_memory()`，以及 `DecisionMemory.filter()`。

恢复时遍历历史日志，仅用 `(seed, class, ascension_level)` 与 mode 匹配，没有用本局 ID 约束。新局从 floor 0 正常进入时通常跳过该恢复路径，但在中途恢复控制器时会触发。

隔离复现使用两条合法的旧局领取/跳过卡牌记录及旧局结束记录，再创建不同 run_id、相同种子的恢复会话：

```text
本局原生候选：claim、proceed
恢复后候选：proceed
```

旧局的“已经跳过这层卡牌奖励”污染了本局，新的合法奖励被程序过滤。这是直接改变候选集合的代码问题。它可能影响恢复后的非战斗行为，但尚未证明此前所有事件跳过或商店不买都由它导致。

### 3.2 计划复用漏掉有语义的字段

位置：`turn_planner.py:24` 的 `projection()` 与 `bind_plan_step()`。

搜索状态保留 `free_to_play_once`，执行匹配投影却不保留。复现将一张打击从免费变成正常收费：旧计划的匹配仍通过，而实际出牌后能量从预期剩 1 变为剩 0。

这证明复用前置条件不完整；它可能影响连招续执行。该反例只验证匹配函数的契约缺陷，尚未证明它造成了此次 END 死亡，也不能等同于首个动作发送前的 revision 检查失效。

## 4. 架构缺口，不冒充已证明的致死原因

| 缺口 | 代码事实 | 后果/待验证点 |
|---|---|---|
| 预测时间点混合 | `rules.outcome()` 的敌人 HP、能量、格挡取自出牌后 state，玩家 HP 取自模拟结算后的 ended | B 看起来像同一“结果”，实际混合了多个时间点。该契约应修正；本次加说明未证明能单独解决模型错误 |
| 知识与建议未分层 | `monsters.encounter_context()` 同时含阈值/机制和建议语句；`simple_combat_payload()` 整体移除 `encounter_mechanics` | 原生 buff 描述仍在，但结构化事实与策略建议无法独立保留 |
| 模型接口没有能力契约 | 当前网关没有独立的最大选项数检查，SDK 构造器也接受 256 项 | 官方上限是 255；枚举出更多项时不能依赖异常字符串才决定如何处理 |
| 错误处理改变决策协议 | 超限处理里同时进行换编码、分组选择、决赛 | 网络/编码处理与策略协议耦合，实验结果难以归因 |
| 请求可追溯性不足 | 常规日志主要保存语义输入和解码后决策，未逐请求保存实际 HTTP body/原始响应 | 以前的概率不一致无法追查是服务、精度还是映射问题 |
| 中央会话职责过多 | session.py 827 行；receive() 249 行；模块中 53 个 self 写入字段 | 状态采集、策略、队列、事务、恢复、统计相互影响，合法状态组合不明确 |
| 测试层级混合 | 很多测试验证模拟器自身结果、固定 mock 选择与协议流转 | “很多测试通过”不能证明模型会避开死亡或合理构筑 |

## 5. 官方接口核对与纠正

查阅官方文档及当前 SDK：

- Choice 接受文本、对象或数组描述；代码传结构化 criteria 本身并非接口误用。
- 官方明确写明 `choice` 是最高概率选项；`probabilities` 是候选分布，不是游戏胜率；confidence 来自分布形状。
- 一个 Choice 最多 255 个选项。SDK 构造 256 项仍成功，因此应用需自己处理能力边界。
- System One 强调快速、集中的判断，不输出推理解释；校准也不保证某次回答正确。

我此前说“要求 choice 与最大概率一致没有依据”不准确。它有官方合同依据。正确处理是把不一致识别为 provider contract anomaly、保存证据并明确处理策略；不应凭空推断含义，也不应直接把诊断异常变成整局停机。此次 30 次请求没有复现这类不一致，不能补判以前那一次的根因。

官方来源：

- https://docs.typesafe.ai/primitives/choice
- https://docs.typesafe.ai/concepts/system-one

## 6. 对重构的要求

优先级不是“再加一条不要 END 的规则”，而是：

1. 修正本局身份、奖励来源身份和计划前置条件，杜绝程序自己删错候选或复用失效计划。
2. 把观察事实、规则知识、预测时间点和策略建议分开。
3. 把“模型选择协议”做成可独立实验和替换的组件；不能假设一个快速分类调用天然承担整局规划。
4. 独立评估致死错误、无代价收益遗漏、机制误判、非战斗收益判断及排列敏感性。
5. 保留原生事务层，继续把收到执行回执与打法好坏分开。

完整重构方案见 `docs/architecture-replan.md`。

证据目录：`logs/architecture-review/verified-static/`、`logs/architecture-review/probes/`。后者包含 30 份实际 HTTP 请求和响应，不含鉴权头；静态检查使用隔离目录，没有改写真实游戏历史。
